# 知识库平台设计文档

状态：待审阅　|　日期：2026-11-10

本文档是动手写代码前的设计稿。标有「待核实」的内容是尚未用实际环境验证的假设，第 12 节集中列出。

## 1. 定位与范围

### 1.1 定位

一个独立的知识库管理平台，做三件事：

1. 把非结构化文档解析、切分、向量化后存入 Milvus。
2. 定义并维护这些数据的结构。
3. 提供带权限校验的基础召回接口。

检索策略（重排序、问题改写、多轮检索、答案生成）不在平台内，由各调用应用自己实现。

### 1.2 第一版包含

| 模块 | 内容 |
|---|---|
| 账号 | 管理员创建（单个或 Excel 批量导入），不开放注册；账号密码登录；重置密码、停用；首次部署自动生成管理员 |
| 服务账号 | 管理员创建，只有密钥，不能登录界面 |
| 密钥 | 每个账号可建多把，可命名、设过期时间、吊销；只在创建时显示一次 |
| 分组 | 管理员建分组、增减成员 |
| 知识库 | 创建、默认切分设置、授权、标记公开、删除、重建索引 |
| 文档 | 上传、切片预览与确认、整份替换、停用、删除、失败重试 |
| 切片 | 查看、编辑、新增、删除、停用 |
| 召回测试页 | 选知识库、输入问题、选检索方式，查看返回的切片和分数 |
| 召回接口 | 见第 8.2 节 |
| 日志 | 操作日志、检索调用记录 |
| 部署 | `deploy/.env` + Docker Compose 一键部署 |

### 1.3 第一版不做

1. 扫描件和图片的 OCR、pptx、表格与插图的版面还原。
2. 重排序、问题改写、答案生成。
3. 切片的历史版本与回滚。
4. 应用内用平台账号登录、以用户本人身份检索。
5. 对接公司统一账号或单点登录。
6. 用量统计报表、检索效果评测。
7. 父子切片、问答对自动生成、摘要索引。
8. 多语言界面（只做简体中文）。

这 8 项都不影响第 5、6 节的数据结构，以后追加不需要推翻现有设计。

## 2. 总体架构

```
浏览器 ──┐                      ┌──> PostgreSQL（业务数据，为准）
         ├─> nginx :8200 ─> api ─┼──> Milvus（检索副本）
调用应用 ┘        │              ├──> MinIO（原始文件）
                  │              └──> Redis（任务队列）
                  └─> 前端静态文件          │
                                         worker（解析、切分、向量化、同步 Milvus）
                                            └──> 公司网关（bge-m3）
```

| 进程 | 职责 |
|---|---|
| `api` | 所有 HTTP 接口。上传文件时只做保存和入队，不做耗时处理 |
| `worker` | 从 Redis 队列取任务：解析、切分、向量化、写 Milvus、重建索引 |
| `nginx` | 统一入口，提供前端静态文件，转发接口请求 |

**数据准绳**：PostgreSQL 是唯一准绳。Milvus 中的每一条数据都能由 PG 中的切片重新生成，所以 Milvus 可以随时清空重建。

### 2.1 技术选型

| 部分 | 选型 |
|---|---|
| 后端 | Python 3.12、FastAPI、SQLAlchemy 2、Alembic |
| 任务队列 | RQ（基于 Redis，简单稳定） |
| 业务数据库 | PostgreSQL 16 |
| 向量库 | Milvus 2.6 单机版，`pymilvus` 2.6 |
| 文件存储 | MinIO |
| 前端 | React、Vite、TypeScript、Ant Design |
| 文档解析 | `python-docx`（docx）、`pdfplumber`（PDF）、`openpyxl`（xlsx） |
| 密码哈希 | argon2 |

### 2.2 访问路径

| 路径 | 用途 | 鉴权 |
|---|---|---|
| `/` | 管理界面 | — |
| `/api/v1/…` | 管理界面使用的接口 | 登录后的 JWT |
| `/open/v1/…` | 给应用调用的召回接口 | API 密钥 |

入口端口暂定 **8200**（已确认本机未占用；8100 留给原诊断助手项目）。

## 4. 权限模型

### 4.1 概念

| 概念 | 说明 |
|---|---|
| 账号 | 个人账号（可登录界面）或服务账号（只有密钥，给应用使用） |
| 分组 | 一批账号的集合，本身不带角色，只用于批量授权 |
| 知识库授权 | 在某个知识库上，授给某个分组或某个账号一个权限档位 |
| 密钥 | 属于某个账号，代表该账号本人 |

全局只有两种身份：**平台管理员**和**普通账号**。另有一个账号级开关「可创建知识库」，由平台管理员设置。

### 4.2 权限档位

高档包含低档。

| 档位 | 能做什么 |
|---|---|
| 只读 | 查看知识库、文档、切片；在召回测试页和召回接口中检索 |
| 编辑 | 上传、替换、停用、删除文档；编辑、新增、删除、停用切片；修改切分设置 |
| 管理 | 修改知识库名称与描述；授权与取消授权；标记公开；重建索引；删除知识库 |

### 4.3 判定规则

某账号在某知识库上的有效权限，按以下顺序取**最高**一档：

1. 账号是平台管理员 → 管理。
2. 该账号被单独授予的档位。
3. 该账号所在的各分组被授予的档位。
4. 知识库标记为公开 → 只读。
5. 以上都没有 → 无权限。

附加规则：

- 创建知识库的账号自动获得一条「管理」授权。
- 账号被停用后，其登录凭证和所有密钥立即失效。
- 每个知识库至少保留一个「管理」授权，否则不允许取消（防止无人可管）。平台管理员始终可以接管。
- 密钥没有独立的权限范围，它能做的事等于其所属账号能做的事。召回接口只要求「只读」。

### 4.4 全局操作的权限

| 操作 | 谁可以 |
|---|---|
| 账号、分组、服务账号的增删改 | 平台管理员 |
| 查看全平台操作日志与检索记录 | 平台管理员 |
| 创建知识库 | 平台管理员，或开启了「可创建知识库」的账号 |
| 管理自己的密钥、修改自己的密码 | 账号本人 |
| 为服务账号创建和吊销密钥 | 平台管理员 |

### 4.5 实现要点

- 权限判定集中在 `auth` 模块的一个函数里：输入账号和知识库，输出有效档位。所有接口都调用它，不在各处自己写判断。
- 批量场景（列出可访问的知识库、一次检索多个库）用一条 SQL 算出该账号在所有知识库上的档位，避免逐个查询。
- 权限每次请求实时计算，不做缓存。授权变更立即生效。数据量大到成为瓶颈时再考虑缓存。

## 5. 业务数据表（PostgreSQL）

主键统一用 32 位十六进制字符串（UUID 去掉连字符），便于直接用作 Milvus 主键和集合名的一部分。所有表都有 `created_at`、`updated_at`，下表不再重复列出。每个字段在建表时都带注释，注释内容即下表「说明」列。

| 字段 | 类型 | 说明 |
|---|---|---|

| `display_name` | varchar(64) | 显示名称 |
| `account_type` | varchar(16) | 账号类型：`person` 个人账号，`service` 服务账号 |

| `must_change_password` | boolean | 下次登录是否必须修改密码 |
| `token_valid_after` | timestamptz，可空 | 此时间之前签发的登录凭证一律失效；修改密码、重置密码、停用账号时更新 |

## 6. Milvus 数据结构

### 6.1 组织方式

一个知识库对应一个集合，集合名 `kb_<知识库 id>`。删除知识库即删除集合。

### 6.2 集合字段

| 字段 | 类型 | 说明 |
|---|---|---|
| `chunk_id` | VARCHAR(32)，主键 | 与 PG 中切片的主键相同 |
| `doc_id` | VARCHAR(32) | 所属文档，用于按文档过滤和删除 |
| `seq` | INT32 | 切片在文档中的序号 |
| `content` | VARCHAR(16384) | 切片正文，原样返回给调用方 |
| `search_text` | VARCHAR(60000)，按空格分词 | 用于关键字检索的词，见 6.2.1 节 |
| `dense_vector` | FLOAT_VECTOR(1024) | `bge-m3` 生成的向量 |
| `sparse_vector` | SPARSE_FLOAT_VECTOR | 由 Milvus 的 BM25 函数根据 `search_text` 自动生成，不需要也不能手工写入 |
| `enabled` | BOOL | 是否参与检索；等于「切片启用且文档启用」 |
| `metadata` | JSON | 与 PG 中切片的元数据相同 |

说明：

- `VARCHAR` 的长度按字节计算，一个汉字占 3 字节。切片正文上限定为 **4000 字**，对应最多 12000 字节，留有余量。
- 只有当前生效版本的切片才写入 Milvus。替换过程中的新版本切片先只存在 PG 里。

#### 6.2.1 检索用文字与切词（第 3 步确定，第 4 步修订）

- **上下文前缀**：参与关键字检索和向量化的文字，都是「文档名（去扩展名）> 章节标题路径」加上切片正文。很多切片本身不含产品型号（例如规格书里的一行参数），型号只出现在文档名或标题里，带上前缀这类切片才能被找到。`content` 字段保持原文不变。
- **切词由平台完成，不用词典分词器**。`search_text` 里存的是切好的词，用空格分开，Milvus 只按空格分词。入库和查询用同一个函数（`search_tokens`）：
  - 汉字：每相邻两个字为一个词。「中转台卡料」→ 中转、转台、台卡、卡料。
  - 字母数字：统一小写，按符号断开。`YDFLP-20-M8` → ydflp、20、m8；`200W` → 200w；带小数的数值保持完整，如 `0.5`、`ezcad2.14.11`。
- **为什么不用 jieba**（第 4 步测试中发现）：jieba 会按上下文猜新词。「卡料」单独出现时是一个词，在「中转台卡料」里却被切成「台卡」「料」，于是搜「卡料」找不到这句话。行业术语大多不在词典里，这是普遍情况。按相邻两字切词的结果与上下文无关，同一个词在任何句子里都能命中。
- 代价：`search_text` 约为原文的 2 到 3 倍大小（4000 字的切片约 3 万字节，字段上限 6 万）；「台卡」这类跨词的两字组合也会成为词，可能带来少量无关命中，排序上会低于真正包含查询词的切片。
- 标题路径包含本节自己的标题，例如「3. 激光器测控软件 > 3.1 软件控制使用说明」。
- **强一致读取**：集合按强一致级别创建，入库、删除、停用之后的下一次检索立刻生效。Milvus 默认的级别允许短暂读到旧数据。

### 6.3 索引

| 字段 | 索引 | 参数 |
|---|---|---|
| `dense_vector` | HNSW，余弦相似度 | `M=16`、`efConstruction=200` |
| `sparse_vector` | SPARSE_INVERTED_INDEX，度量为 BM25 | `bm25_k1=1.2`、`bm25_b=0.75`、`inverted_index_algo=DAAT_MAXSCORE` |
| `doc_id` | 标量索引 | 加速按文档过滤和删除 |

现有项目用的是 IVF_FLAT；这里改用 HNSW，因为单个知识库数据量不大，HNSW 无需调参且召回率更高。

### 6.4 同步规则

| PG 中的操作 | Milvus 中的动作 |
|---|---|
| 文档入库完成 | 批量写入该文档的全部切片 |
| 编辑切片正文 | 重新向量化，整行覆盖该切片 |
| 新增切片 | 写入一条；其后各片的序号用字段更新顺延 |
| 删除切片 | 删除一条；其后各片的序号用字段更新前移 |
| 停用、启用切片或文档 | 只更新 `enabled` 字段，不重新向量化 |
| 修改文档标签 | 只更新 `metadata` 字段 |
| 整份替换或重新切分完成 | 写入新版本切片，再删除旧版本切片 |
| 删除文档 | 按 `doc_id` 删除 |
| 删除知识库 | 删除集合 |

- 「只更新个别字段」已在 Milvus 2.6.27 上验证：带关键字检索函数的集合支持，更新后关键字检索正常，向量保持不变。
- 切片的手工维护是同步完成的：先写 Milvus，成功后再提交数据库；向量模型或 Milvus 不可用时返回 503，数据库不变，两边保持一致。一次修改正文约 0.5 秒。
- 管理界面提供「重建索引」作为兜底，从 PG 重新生成整个集合。

### 6.5 容量预估

1024 维向量每条约 4KB，连同索引粗略估算：10 万条切片约 0.6GB 内存，100 万条约 6GB。这是经验估算，不是实测值。本机 15GB 内存且与其他容器共用，预计百万条以内可用；超过后可改用磁盘索引、开启内存映射，或把 Milvus 迁到独立机器，应用无需改动。

所有集合都需要加载到内存才能检索。知识库数量在几十个的量级没有问题；到上千个时需要改为按需加载，第一版不处理。

## 7. 文档处理

### 7.1 文档状态

```
上传 → parsing 解析中 → pending_confirm 待确认 → embedding 向量化中 → ready 可用
              │                                          │
              └────────────── failed 失败（可重试）───────┘
```

| 状态 | 说明 |
|---|---|
| `parsing` | 已保存原始文件，正在提取文字并按设置切分 |
| `pending_confirm` | 切片已生成并存入 PG，等待操作者预览确认；此时可修改切分设置后重新切分 |
| `embedding` | 已确认，正在向量化并写入 Milvus |
| `ready` | 可检索 |
| `failed` | 失败，`error_message` 记录原因，可重试 |

「停用」是独立的开关（`enabled`），不是状态。

上传时可勾选「跳过确认」，解析完成后直接进入向量化，用于批量上传格式已知的文件。

### 7.2 各格式的解析方式

| 格式 | 处理 |
|---|---|
| txt、md | 自动识别编码（UTF-8、GBK）后读取 |
| docx | 按段落提取文字，保留标题层级；表格逐行转为「列名：值」的文字 |
| PDF | 逐页提取文字并记录页码。若平均每页提取到的文字少于 20 字，判定为扫描件，处理失败并提示「不支持扫描件」 |
| xlsx、csv | 每行转为「列名：值；列名：值」的一段文字，每个工作表单独处理 |

单个文件大小上限 50MB，可配置。同一知识库内不允许上传内容完全相同的文件（按内容哈希判断）。

第 3 步用样本验证后确定的处理细节：

- PDF：去掉在多数页重复出现的页眉、页脚、页码和目录行；相邻的折行合并成段落。
- PDF 的标题靠编号识别（「1.4 标题」「3. 标题」）。一级标题和表格行、操作步骤（「3 串行时钟」）形式相同，所以只接受编号恰好接在上一章之后的那一个。这是经验规则，个别说明书可能识别不全，靠切片预览发现。
- 表格（docx 中的表格、xlsx、csv）：每行转成「列名：值；列名：值」；整行只有一个内容的行视为分组标题，加在其后各行前面，如「光学特性｜型号指标：额定输出功率（中心）；W；…：1000」。两列的表按「名称：内容」处理。
- 相邻切片的重叠部分从一行或一句的开头取起；表格行不会被从中间截断。
- 没有实际内容（只有符号）的切片自动丢弃；单个文档最多 20000 个切片。

### 7.3 切分设置

`chunk_config` 的结构：

```json
{
  "mode": "separator | length | heading",
  "separator": "## query",
  "chunk_size": 500,
  "overlap": 50,
  "heading_level": 2
}
```

| 方式 | 行为 | 适用 |
|---|---|---|
| 按分隔符 `separator` | 遇到分隔符就切开，分隔符保留在下一片的开头。超过 4000 字的片再按长度切 | 问答文件，如以 `## query` 分隔的常见问题 |
| 按长度 `length` | 以段落为单位聚合到 `chunk_size` 字，相邻片重叠 `overlap` 字，尽量不在句子中间断开 | 没有明显结构的普通文档 |
| 按标题层级 `heading` | 按不深于 `heading_level` 的标题切开，把标题路径（如「第三章 > 3.2 调焦」）写入元数据；超过 `chunk_size` 的章节在章节内再按长度切 | 有章节结构的 md、docx 说明书 |

知识库保存一份默认设置，上传单个文档时可以覆盖。

### 7.4 向量化

- 调用公司网关的 `bge-m3`，接口为 OpenAI 兼容格式（`{"model": …, "input": [文本…]}`），沿用现有项目的调用方式：每批 32 条，遇到限流按退避时间重试，最多 5 次。
- 入库和查询使用同一个模型配置，保证一致。

### 7.5 整份替换与重新切分

两者都是为已入库的文档准备一个新版本，区别只是新版本来自新文件还是原文件加新的切分设置。

1. 发起后文档状态变为 `parsing`，新版本的切片以 `generation + 1` 写入 PG。此时旧版本的切片仍在 Milvus 中，照常可以检索。
2. 新版本走「待确认 → 向量化」。重新切分一律先预览再确认；替换可以勾选跳过确认。
3. 向量化完成后：新切片写入 Milvus，再删除旧切片，文档的 `generation` 加一，文件名等信息换成新文件的，旧文件删除。
4. 任何一步失败，旧版本不受影响；可以重试，也可以「取消」，放弃新版本回到已入库的版本。
5. 准备新版本期间，已入库的切片不能手工修改。
6. 已入库的版本里有手工修改或手工新增的切片时，发起前会被拦下并告知数量，操作者明确确认丢弃后才能继续。
7. 新文件的内容与当前版本相同、或与本知识库其他文档相同时拒绝。文档的标签沿用。

### 7.6 切片的手工维护

可以维护两种切片：

- **已入库的**（文档状态为「可用」）：修改立刻同步到 Milvus，下一次检索就生效。
- **待确认的**（文档状态为「待确认」）：只改 PG，确认入库时按改过的内容处理。

| 操作 | 说明 |
|---|---|
| 修改正文 | `is_edited` 置为真 |
| 停用、启用 | 停用的切片搜不到，也不能通过召回接口按编号取到；取相邻切片时被跳过 |
| 新增 | 可指定插入位置，其后的切片序号顺延；`origin` 为 `manual` |
| 删除 | 其后的切片序号前移；文档的最后一个切片不能删 |

文档的停用和启用独立于切片：重新启用文档后，原先单独停用的切片仍是停用的。

## 8. 接口

### 8.1 管理接口（`/api/v1`，JWT 鉴权）

只列出资源和操作，字段在实现时按第 5 节的表结构展开。

| 资源 | 操作 |
|---|---|
| `/auth` | 登录、退出、修改自己的密码、查看当前账号 |
| `/accounts` | 列表、创建、批量导入、修改、停用、重置密码 |
| `/accounts/{id}/keys`、`/me/keys` | 列表、创建、吊销 |
| `/groups`、`/groups/{id}/members` | 分组与成员的增删改查 |
| `/knowledge-bases` | 列表（只返回有权限的，并标明自己的档位）、创建、修改、删除、重建索引 |
| `/knowledge-bases/{id}/grants` | 授权的列表、新增、修改、取消 |
| `/knowledge-bases/{id}/documents` | 列表、上传 |
| `/documents/{id}` | 详情、停用或启用、修改标签、删除；`/rechunk`、`/confirm`、`/retry`、`/replace`、`/cancel-replace` |
| `/documents/{id}/chunks` | 列表、新增 |
| `/chunks/{id}` | 修改正文、停用或启用、删除 |
| `/recall-test` | 召回测试，参数与召回接口相同，可同时选多个知识库 |
| `/logs/operations`、`/logs/retrievals` | 日志查询。平台管理员看全部；其他账号必须指定一个自己有管理权限的知识库 |

登录凭证有效期默认 12 小时，可配置。

第 2 步实现时补充的规则：

- 密码不限制长度和字符（用户决定，2026-11-10），只要求非空、且修改时不能与原密码相同。管理员创建或重置的密码都是一次性的，首次登录必须修改；修改之前只能查看自己和改密码。
- 同一登录名连续输错 5 次，锁定 10 分钟。登录名不存在和密码错误返回相同的提示。
- 修改密码、重置密码、停用账号后，该账号此前签发的登录凭证立即全部失效。
- 账号只能停用，不能删除，以保证日志可追溯。管理员不能修改自己的管理员身份和启用状态，保证始终至少有一个可用的管理员。
- 个人账号的密钥只能由本人创建；管理员只能为服务账号创建密钥，但可以吊销任何账号的密钥。每个账号最多 20 把未吊销的密钥。
- 另有 `/directory`（所有登录账号可用，按关键字查找账号和分组，供授权时选择）、`/accounts/import-template`（下载导入模板）、`/open/v1/me`（验证密钥并返回其代表的账号）。
- 批量导入的表头为：登录名、显示名称、初始密码（可空）、分组（可空，多个用分号分隔）。逐行处理，出错的行跳过并说明原因。

### 8.2 召回接口（`/open/v1`，API 密钥鉴权）

所有请求在请求头携带：`Authorization: Bearer kb-xxxxxxxx`

#### 8.2.1 检索

`POST /open/v1/retrieval/search`

请求：

```json
{
  "query": "200W红外划线机中转台卡料怎么处理",
  "kb_ids": ["a1b2…", "c3d4…"],
  "mode": "hybrid",
  "top_k": 10,
  "score_threshold": null,
  "filter": {
    "doc_ids": ["…"],
    "tags": {"产品线": "划线机"}
  }
}
```

| 参数 | 必填 | 说明 |
|---|---|---|
| `query` | 是 | 查询文本，最长 2000 字 |
| `kb_ids` | 是 | 要检索的知识库，1 到 10 个 |
| `mode` | 否 | `vector` 向量检索，`keyword` 关键字检索，`hybrid` 两路融合。默认 `hybrid` |
| `top_k` | 否 | 返回条数，默认 10，上限 50 |
| `score_threshold` | 否 | 只在 `vector` 模式下有效，丢弃相似度低于该值的结果 |
| `filter.doc_ids` | 否 | 只在这些文档内检索 |
| `filter.tags` | 否 | 文档上传时填写的自定义标签必须全部相等 |

响应：

```json
{
  "mode": "hybrid",
  "score_type": "rrf",
  "took_ms": 86,
  "results": [
    {
      "chunk_id": "…",
      "kb_id": "…",
      "kb_name": "调阻机常见问题",
      "doc_id": "…",
      "doc_name": "调阻机常见问题.txt",
      "seq": 12,
      "content": "## query：…",
      "score": 0.0312,
      "metadata": {"heading_path": null, "page": null, "tags": {}}
    }
  ]
}
```

检索过程：

1. 校验密钥，得到账号。
2. 逐个检查 `kb_ids` 的权限。只要有一个不存在或无只读权限，整个请求返回 403，并列出是哪些。不存在和无权限返回相同的错误，避免泄露知识库是否存在。
3. `vector` 和 `hybrid` 模式下，调用 `bge-m3` 把查询文本转成向量。
4. 并行查询各知识库的集合，过滤条件始终包含 `enabled == true`。
5. 合并各库的结果，截取前 `top_k` 条返回。
6. 写一条检索记录。

**各模式的打分与跨库合并规则**

响应里的 `score_type` 说明本次 `score` 的含义。

| 模式 | 只检索一个库 | 检索多个库 |
|---|---|---|
| `vector` | 余弦相似度，`cosine` | 所有库使用同一模型，相似度可直接比较，按分数合并，`cosine` |
| `keyword` | Milvus 给出的 BM25 分，`bm25` | 各库的 BM25 分依赖各自的词频统计，不可直接比较，按各库内的名次合并，`rrf` |
| `hybrid` | 向量与关键字各取 `max(top_k × 2, 20)` 条，用 RRF 融合，`rrf` | 各库先各自融合，再按各库内的名次合并，`rrf` |

- RRF 常数固定为 60，不对外开放。
- 按名次合并的含义：每个库的第 1 名同等重要，然后是各库的第 2 名，依此类推；同名次之间按请求中知识库的先后顺序。分数为 `1 / (60 + 名次)`。应用若需要更精确的跨库排序，应在拿到结果后自行重排序。
- 只有 `cosine` 可以跨请求比较，`score_threshold` 因此只在 `vector` 模式下生效。
- 关键字检索只返回真正包含查询词的切片，条数可能少于 `top_k`，也可能为零。
- 查询文本向量化遇到网关限流或临时故障时，只做 3 次很短的重试（共约 1.7 秒），仍失败则返回 503，由应用决定是否改用关键字检索。入库时的重试则耐心得多。

实测耗时（样本库 264 个切片，单库，2026-11-10）：关键字检索约 12 毫秒；向量和融合检索约 105 毫秒，其中约 90 毫秒是调用网关把查询文本转成向量。

#### 8.2.2 辅助接口

| 接口 | 说明 |
|---|---|
| `GET /open/v1/knowledge-bases` | 列出当前密钥可访问的知识库（id、名称、描述、文档数、自己的档位） |
| `GET /open/v1/knowledge-bases/{kb_id}/chunks/{chunk_id}` | 按切片 ID 取原文 |
| `GET /open/v1/knowledge-bases/{kb_id}/chunks/{chunk_id}/neighbors?before=1&after=1` | 取同一文档中前后相邻的切片，各最多 5 条 |

#### 8.2.3 错误

统一格式：`{"code": "KB_FORBIDDEN", "message": "…", "detail": {…}}`

| HTTP 状态 | `code` | 情况 |
|---|---|---|
| 400 | `INVALID_PARAM` | 参数缺失或超出范围 |
| 401 | `INVALID_KEY` | 密钥不存在、已过期、已吊销，或所属账号已停用 |
| 403 | `KB_FORBIDDEN` | `kb_ids` 中有不存在或无权限的知识库，`detail.kb_ids` 列出 |
| 404 | `NOT_FOUND` | 切片不存在 |
| 409 | `KB_REBUILDING` | 有知识库正在重建索引，`detail.kb_ids` 列出 |
| 409 | `KB_NEEDS_REBUILD` | 有知识库入库时的向量模型与当前配置不同，不能做向量检索（关键字检索不受影响），`detail.kb_ids` 列出 |
| 503 | `EMBEDDING_UNAVAILABLE` | 向量模型服务不可用（`keyword` 模式不受影响） |
| 503 | `VECTOR_STORE_UNAVAILABLE` | Milvus 不可用 |

## 9. 配置与部署

### 9.1 部署方式

沿用 Dify 式的一键部署：部署人员只需要填写 `deploy/.env`，然后执行 `docker compose up -d`。

- `deploy/.env` 只放公共变量，每个值填一次，由 `docker-compose.yaml` 组装成各容器需要的变量。
- PG、Redis、MinIO、Milvus（及其依赖 etcd）默认一起部署，可用 `COMPOSE_PROFILES` 改为使用外部已有的组件。
- 首次启动自动生成密钥、执行数据库迁移、创建管理员账号（初始密码写入 `deploy/volumes` 下的文件，首次登录强制修改）。
- 数据、日志、密钥都放在 `deploy/volumes/`。
- 镜像在服务器上直接构建，pip 和 npm 的源可配置。
- `backend/.env` 只用于不走 Docker、用 `manage.sh` 单独启动的情况。两套配置都提供 `.env.example`。

### 9.2 主要配置项

| 配置 | 说明 |
|---|---|
| `EXPOSE_PORT` | nginx 对外端口，默认 8200 |
| `EMBEDDING_URL`、`EMBEDDING_MODEL`、`EMBEDDING_API_KEY`、`EMBEDDING_DIM` | 向量模型，默认 `bge-m3`、1024 维 |
| `EMBEDDING_BATCH_SIZE`、`EMBEDDING_MAX_RETRIES` | 每批条数与重试次数，默认 32、5 |
| `DB_*`、`REDIS_*`、`MINIO_*`、`MILVUS_*` | 各组件的连接信息 |
| `SECRET_KEY` | 登录凭证的签名密钥，首次启动自动生成 |
| `TOKEN_EXPIRE_HOURS` | 登录有效期，默认 12 |
| `UPLOAD_MAX_SIZE_MB` | 单文件上限，默认 50 |
| `RETRIEVAL_LOG_KEEP_DAYS` | 检索记录保留天数，默认 30 |

更换向量模型后，已有知识库记录的模型名与当前配置不一致，界面会提示这些库需要重建索引后才能检索。

### 9.3 网络

- `api` 只监听容器内部网络，所有访问经过 nginx。
- `/open/v1/` 是否限制来源 IP 由部署时决定，默认不限制，靠密钥鉴权。

## 12. 待核实与风险

动手写相关代码前逐项验证，结果回填本文档。

| 编号 | 事项 | 现状 | 若不成立的应对 |
|---|---|---|---|
| 1 | Milvus 版本 | 官方文档站当前默认显示 3.0.x；现有项目使用 `pymilvus` 2.6.12，本机已有的镜像是 2.5.4。**已决定使用 2.6**（2026-11-10），与现有项目的客户端版本一致 | 两者的全文检索用法基本一致，将来升级到 3.0 不需要改数据结构 |
| 2 | 中文分词对型号的处理 | **已解决，见 6.2.1 节。**实测记录（2026-11-10，Milvus 2.6.27，内置分词器）：`200W`、`E-101`、`DB15`、`1000W` 保持完整；但长型号被切得不规则，`YDFLP-20-M8` 切成 `YDFLP-20` 和 `M8`，`AOB-1000/1000-L2-W-K-10` 切成 `AOB-1000`、`1000`、`L2`、`W`、`K-10`。查询和入库用同一个分词器，所以输入完整型号能命中；但只输入 `YDFLP` 或 `AOB` 这样的型号前缀时，关键字检索命中不了 | 已改用自定义分词器并在入库和查询时拆分型号 |
| 3 | 带 BM25 函数的集合是否支持原地更新 | **已验证（2026-11-10，2.6.27）**：整行覆盖和只更新个别字段都支持，关键字检索不受影响。停用、调整序号、改标签因此不需要重新向量化 | 设计中已统一采用「先删除再写入」，不依赖原地更新 |
| 4 | `bm25_b` 参数的含义 | 2.6 与 3.0 两版文档的描述相反，疑为 2.6 文档笔误 | 使用默认值 0.75，不做调整 |
| 5 | 网关上 `bge-m3` 的维度与批量上限 | **已验证（2026-11-10）**：返回 1024 维、已归一化的向量；每批 32 条正常；4000 字的长文本正常。三份样本共 264 个切片，从上传到全部入库约 10 秒。网关上的重排序模型与向量模型共用同一把密钥、模型名不同；平台本身不调用重排序，由应用自行调用 | — |
| 6 | 文字版 PDF 的提取质量 | 多栏排版、带表格的说明书可能出现文字顺序错乱 | 靠切片预览发现问题；严重时建议先转成 docx 再上传，或在第二版引入版面解析 |
| 7 | 内存 | 本机 15GB，与二十多个容器共用。**实测（空库）**：五个基础组件合计约 380MB，其中 Milvus 约 150MB；有数据后会增长 | 数据量增长后改磁盘索引或迁移到独立机器 |
| 8 | MinIO 镜像来源 | **第 1 步发现**：本机从 Docker Hub 拉取 `minio/minio` 被拒绝，quay.io 超时。目前用的是本机已有的镜像（发行版本 `RELEASE.2025-09-07T16-13-09Z`），在新服务器上无法直接拉取 | 第 7 步部署收尾时确定：从本机导出镜像随部署包分发，或改用公司可访问的镜像源 |

### 12.1 样本文件带来的补充（2026-11-10）

用户提供了三份样本（位于上级目录的 `data/`，不进仓库）。查看后对第 7 节补充如下，在第 3 步实现：

| 样本 | 观察 | 对实现的要求 |
|---|---|---|
| `20-M8脉冲光纤激光器说明书V03.pdf`（30 页） | 文字版，可正常提取。每页开头都有页眉「YDFLP-20-M8 使用说明书」和页码；章节标题是「1.4 YDFLP 系列命名规则」这样的编号文字，没有书签；有 3 页文字不足 100 字（以图为主） | 去除在多数页重复出现的页眉页脚行；PDF 的「按标题层级切分」靠识别编号标题实现；扫描件判定按全文平均而不是单页 |
| `AOB-1000_1000-L2-W-K水冷连续光纤激光器规格书_V1.1.docx` | 正文几乎全在 6 张参数表里，共约 2500 字；没有使用标题样式；表格行形如「额定输出功率（中心）｜W｜1000」，并用「光学特性」这样的行作分组 | 表格每行转成文字时带上分组名和文档中的产品型号，否则单独一行「W 1000」无法被检索到；没有标题样式的 docx 自动退回按长度切分 |
| `调阻机常见问题.txt` | 以 `## query` 分隔的问答 | 按分隔符切分，每片一问一答 |

## 13. 实施顺序（建议）

每一步结束时都能实际运行和验证。

1. **骨架**：目录、配置、日志、数据库迁移、Docker Compose、健康检查。
2. **账号与权限**：账号、登录、分组、密钥、权限判定函数。
3. **知识库与文档入库**：知识库与授权、上传、三种切分、预览确认、向量化、写入 Milvus。先核实第 12 节的 1、2、3、5 项。
4. **召回接口**：三种检索方式、跨库合并、辅助接口、检索记录。
5. **维护能力**：切片编辑、整份替换、停用、重建索引、失败重试。
6. **管理界面**：与第 2 至 5 步对应的页面，以及召回测试页。
7. **部署收尾**：一键部署验证、接口文档、`.env.example`。

用 `data/调阻机常见问题.txt` 作为贯穿第 3、4 步的验证数据：按 `## query` 切分后，每个切片应恰好是一问一答。
